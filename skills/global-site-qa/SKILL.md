# Global Site QA

Perform a complete website audit from the perspective of a real user, QA engineer, API tester, backend verifier, and system safety reviewer.

The goal is not to prove that pages render. The goal is to prove that important user actions produce real backend effects, persist correctly, remain consistent across pages, and survive refresh and regression.

## Core Rule

Every critical feature must be verified as a complete chain:

```text
User Action
→ Frontend Handler
→ Network Request
→ API Route
→ Backend Logic
→ Database / External API
→ Response
→ Frontend Refresh
→ User-visible Result
```

If a critical link is missing, stale, mocked unintentionally, or only represented by UI state, mark it as a failure.

Never mark a feature PASS only because:

- the page looks correct;
- an `onClick` handler exists;
- an HTTP request returned 200;
- code contains a `fetch()` call;
- no obvious error appeared.

## Default Mode

Unless the user narrows scope, run a `FULL-SITE AUDIT`.

Before testing, discover the actual project structure and deployment target. Read the repository rather than assuming routes or architecture from prior context.

Record at minimum:

```text
branch
commit
runtime
framework
database
deployment environment
site URL
```

## Phase 0 — Project Discovery

Inspect the actual project files relevant to execution and testing, including where present:

```text
README
AGENTS.md
package.json
routes/pages/app
components
API routes
lib/services
database schema
migrations
workers/schedulers
config/environment
tests
```

Build a map of how the frontend, backend, database, workers, schedulers, and external services connect.

Do not modify production code during discovery.

## Phase 1 — Build a Site Map

Discover all user-accessible routes from the codebase and the running site.

For each route record:

```text
Route:
Purpose:
Main actions:
APIs used:
Auth requirement:
Status:
```

Test every meaningful route, not only the home page.

## Phase 2 — Page Load Audit

For every page verify:

- expected HTTP response;
- successful render;
- no white screen;
- no infinite loading;
- no hydration/runtime exception;
- no required asset failure;
- no obviously broken layout.

Check console and network output during page load.

Record 4xx/5xx responses, aborted requests, CORS errors, resource failures, React warnings, hydration issues, and uncaught promise rejections.

## Phase 3 — UI Component Audit

Exercise interactive components, including where present:

```text
buttons
links
forms
inputs
textareas
selects
toggles
tabs
modals
dropdowns
navigation
pagination
tables
charts
cards
```

Look for:

- blank buttons or missing labels;
- click with no effect;
- incorrect disabled/enabled state;
- duplicate submission;
- missing loading/success/error feedback;
- broken modal behavior;
- unusable controls;
- wrong route transitions;
- stale data after mutation.

## Phase 4 — Button Reality Test

For every important action, trace the actual chain from UI to backend.

Example:

```text
Button
→ Handler
→ API
→ Backend
→ State Change
→ UI Result
```

If UI says `RUNNING`, `SAVED`, `CONNECTED`, `FILLED`, or similar, confirm the backend state agrees.

If the UI changes without the backend effect, classify it as `FAKE STATE` and fail the test.

## Phase 5 — Network Audit

Observe and classify real requests generated by the site.

Cover all relevant methods:

```text
GET
POST
PUT
PATCH
DELETE
```

Record failures including:

```text
400 401 403 404 409 422 429
500 502 503 504
timeout
abort
CORS
parse failure
```

For each important failure capture:

```text
endpoint
method
status
user action
visible symptom
request stage
```

Never expose secrets, Authorization headers, API keys, private keys, session tokens, or decrypted credentials in the report.

## Phase 6 — API Contract Testing

Enumerate the project's meaningful API routes.

For critical APIs test, where safe and applicable:

- valid input;
- invalid input;
- missing required input;
- boundary values;
- unauthorized access;
- duplicate request/idempotency behavior;
- downstream failure behavior.

Verify:

```text
HTTP status
response schema
error schema
side effects
persistence
idempotency
```

Do not run destructive tests against production data unless explicitly approved and safely isolated.

## Phase 7 — Frontend/API Consistency

Explicitly detect these high-value failures:

```text
API succeeds but UI stays stale
API fails but UI reports success
UI reports RUNNING but backend is STOPPED
UI reports SAVED but refresh loses the data
UI reports CONNECTED but no usable credential/provider exists
```

Treat these as functional failures, not cosmetic issues.

## Phase 8 — Database and Persistence Consistency

For state-changing actions, verify before/action/after state when database access is available.

Check for:

- duplicate rows;
- partial writes;
- orphan rows;
- wrong owner/user scope;
- stale records;
- incorrect timestamps;
- lost state after browser refresh;
- mismatched aggregate values.

A successful HTTP response is not sufficient proof of persistence.

## Phase 9 — Refresh and Cross-page Consistency

After important mutations:

1. Observe the immediate UI.
2. Wait for normal automatic refresh/polling.
3. Refresh the browser manually.
4. Visit another page displaying the same data.

The state should remain consistent.

Examples of failures:

```text
Dashboard shows 1 position, Positions shows 0
Chat shows a reply, refresh removes it
Run shows active, another page shows stopped
Balance changes on one screen but not another
```

## Phase 10 — External API Verification

For every important external service actually used by the product, verify a real runtime request rather than only inspecting static code.

Examples can include:

```text
AI/model providers
market data
weather
sports
news
payments
email
maps
```

For each service confirm as far as observability permits:

```text
request issued
HTTP response received
response parsed
result consumed by application
user-visible or persisted effect
```

Do not print secret values.

If runtime evidence is unavailable, mark the result `UNVERIFIED`, not PASS.

## Phase 11 — AI / Model API Testing

For model-powered features verify the complete chain:

```text
User action
→ application API
→ real model API
→ non-empty response
→ parser/validation
→ persistence if expected
→ UI display
```

Test safe failure handling for relevant cases such as:

```text
401/403 credential failure
402/quota or billing failure where provider uses it
429 rate limit
timeout
invalid model
empty response
invalid structured output
provider unavailable
```

Do not use a hard-coded string as proof of a real model response.

## Phase 12 — Loading and Error UX

For asynchronous actions inspect:

```text
initial
loading
success
failure
retry
```

Detect:

- permanent disabled state;
- stuck spinner/loading text;
- double submit;
- premature success message;
- failure with no visible explanation;
- error displayed too far from the initiating action to be understandable.

## Phase 13 — Race and Duplicate Action Testing

Where safe, exercise:

```text
double click
rapid submit
start twice
stop twice
refresh during mutation
retry after timeout
```

Look for duplicate jobs, duplicate rows, duplicate orders, conflicting state transitions, and lost updates.

## Phase 14 — Responsive and Navigation Testing

At minimum inspect desktop, tablet, and mobile-sized layouts when the toolchain supports them.

Check:

- navigation;
- touch targets;
- forms;
- modal visibility;
- tables and charts;
- overflow;
- overlapping or clipped text;
- hidden/unreachable buttons.

Also test:

```text
sidebar/top nav
browser back
browser forward
refresh
deep links
```

## Phase 15 — Empty and Large Data States

Where feasible test empty states such as:

```text
0 positions
0 orders
0 messages
0 results
0 alerts
```

No page should expose raw `undefined`, `null`, `NaN`, `[object Object]`, crash, or hang.

For list-heavy pages, also inspect behavior with larger datasets if fixtures or safe existing data make this practical.

## Phase 16 — Security Sanity Check

Inspect obvious secret exposure surfaces:

```text
browser storage
console logs
network responses
rendered HTML
error messages
source-visible config
```

Never reveal or copy secret material into the report.

Treat any exposed credential, token, private key, signing secret, or privileged bearer value as critical.

## Kalshi / Trading Safety Override

If the project is a Kalshi or trading-related research system, preserve its declared safety boundary.

For a PAPER-ONLY system:

- never submit a real order;
- never send a production trading write request;
- never use real funds;
- do not use a demo environment to place a real demo order unless the user explicitly changes the safety boundary;
- public/read-only market data is allowed;
- local or isolated paper orders/fills and deterministic fixtures are allowed.

If a real-trading write path is discovered, do not invoke it. Report it as a critical safety finding.

## Phase 17 — Business Workflow Testing

Identify and execute complete core user journeys rather than isolated button checks.

For a PAPER-ONLY Kalshi system, a representative flow is:

```text
Create paper run
→ Start automation
→ Market scan
→ Strategy decision
→ Paper order
→ Paper fill
→ Position
→ Ledger
→ Equity
→ UI refresh
→ Stop automation
```

Use deterministic fixtures or existing safe test mechanisms where a guaranteed trade is needed for validation. Never force production strategy logic to BUY merely to make a test pass.

## Phase 18 — Regression

For each repaired defect use:

```text
Reproduce
→ Fix
→ Verify
→ Regression
```

Re-run the affected user flow and relevant adjacent flows.

Do not claim a bug is fixed only because the code changed.

## Severity

Use this severity model:

```text
P0 CRITICAL
Security boundary breach, real-funds risk, destructive data loss, site unusable.

P1 HIGH
Core user workflow unavailable or materially incorrect.

P2 MEDIUM
Partial malfunction, stale state, inconsistent data, recoverable API/UX issue.

P3 LOW
Cosmetic, copy, minor accessibility, or low-impact usability defect.
```

## Integration With Other Skills

### scoutqa-test

If `scoutqa-test` is available, reuse it for browser-driven exploratory testing, responsive checks, UI interactions, console/network observation, and user journey verification.

`global-site-qa` remains the orchestrator and final acceptance layer.

Do not duplicate ScoutQA capabilities unnecessarily.

### free-gpt-codex-router / free-gpt-codex-router-plus

This skill is primarily for testing and audit.

Only use a coding router when the user explicitly asks for `TEST + FIX` or otherwise authorizes repair work.

Router-generated code is always an unverified candidate. After any repair, rerun relevant native tests, browser/E2E tests, and this global acceptance workflow before marking the issue resolved.

## Completion Condition

Do not end a full-site audit until the practical reachable scope has covered:

- all major pages;
- all critical UI actions;
- core APIs;
- core business workflows;
- persistence and cross-page state;
- relevant external APIs;
- console/network failures;
- responsive behavior;
- security sanity checks;
- regression for critical repaired defects when repair is in scope.

If a required area cannot be tested because credentials, deployment access, tooling, or fixtures are unavailable, explicitly mark it `UNVERIFIED` and state what prevented verification.
